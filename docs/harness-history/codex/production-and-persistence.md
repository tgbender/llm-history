# Codex history production and persistence

Reviewed 2026-11-07 against `openai/codex` revision `2bc8e7f5459b084afa482c7aac3f56fef36286b3`. This is a source review; upstream builds and tests were not run. The adjacent [persistence matrix](persistence-matrix.json) inventories **86 EventMsg variants and 13 RolloutItem variants** checked against their Rust enum definitions. Its policy classifications cover that inventory. The JSON also catalogs 81 distinct direct event payload declarations, retaining field types, declaration attributes, serde/custom-codec annotations, and pinned source links; nested families are documented in the companion schema catalogs. Producer navigation evidence is explicitly distinguished from a verified constructor: matching or forwarding sites can occur alongside construction sites, and tests embedded in production modules can occur in the lexical candidate list.

## Historical acceptance and importer behavior

All persistence classifications in this document describe the pinned revision's live writer. Saved history can contain currently filtered events. The upstream reader deserializes rollout lines independently of the live persistence predicate, and a targeted test preserves old `GuardianAssessment` lines even though current writes filter that event. Migration keeps historical `InterAgentCommunication` and `SecurityRiskScore` representations. These decoder and migration paths establish handling requirements independently of present-day producer provenance. [Typed line reader](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/lib.rs#L77), [historical guardian preservation test](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder_tests.rs#L412), [migration passthrough](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/thread-store/src/local/rollout_migration/canonicalizer.rs#L285).

This repository's open `Record` reader preserves original JSON, payloads, and extras for all event/record kinds, including unknown future kinds and fields. Its current semantic decoder recognizes `task_started` to update turn state and `token_count` to derive usage/token details. Other EventMsg payloads currently remain raw-only for event-specific projections; the `turn_started` alias also currently remains raw-only there. The JSON matrix states that importer disposition for every variant. Expanding semantic projections should retain raw source and extras throughout. See [open envelope reader](../../../crates/ingest/src/codex/record.rs), [implemented projections](../../../crates/ingest/src/codex/decode.rs), and [future-kind retention tests](../../../crates/ingest/tests/codex.rs).

The current upstream serde enum skips `NetworkApprovalResolved` and `PrivateSessionEvent`, so its strict decoder rejects those runtime variants if encoded as saved event tags. This repository's open reader still preserves such JSON. Future unknown enums likewise remain raw data with an explicit projection gap; the checked current enum inventory defines this review's coverage, rather than the lifetime of Codex history formats.

## Canonical write boundary

Core's `Session::persist_rollout_items` forwards a batch to `LiveThread::append_items` when a live handle exists. `send_event_raw_with_persistence` wraps only the `EventMsg` payload, rather than its outer submission `Event.id`, in `RolloutItem::EventMsg`, attempts persistence, records tracing separately, then delivers the event. Realtime reduction can append facts before or after that event under its history lock. The private guardian completion path flushes before parent delivery. A persistence failure is logged and ordinary event delivery proceeds. [Session event and persistence routing](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L2930); [append helper](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L5320)

`LiveThread` computes the filtered set for metadata/telemetry but passes raw items to the store; the local store's per-thread writer lock applies `into_persisted_rollout_items` before queueing canonical items. Its `durable_write(AppendItems)` queues and then awaits `recorder.flush()`. Paginated SQLite materialization begins after that barrier and may lag canonical JSONL on projection error. The recorder's `record_canonical_items` is an already-filtered lower-level API, so directly calling it bypasses policy. The unloaded-thread `append_rollout_item_to_path` also explicitly accepts an already-filtered item. [LiveThread append](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/thread-store/src/live_thread.rs#L255); [local canonical write and projection](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/thread-store/src/local/live_writer.rs#L414)

`config.ephemeral` creates no live persistence handle. New recorders can hold metadata and appended items in memory until `persist`, `flush`, or shutdown materializes them; an empty deferred flush/shutdown leaves the file absent. `send_event_raw_without_materializing_rollout` can suppress persistence based on whether an existing rollout is materialized. These lifecycle conditions qualify every matrix entry marked durable. A live append allowlist describes current writes; older readable records may include events now filtered. [ephemeral initialization](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/session.rs#L1191); [deferred writer barriers](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L1796)

## Event policy and notification boundaries

The authoritative match persists `TokenCount`, `ThreadGoalUpdated`, `ThreadRolledBack`, `TurnAborted`, `TurnStarted`, `TurnComplete`, and `ThreadSettingsApplied` in both history modes. `ThreadRolledBack` is documented as an old replay marker; live rollback operations are unsupported. Wire tags for the turn endpoints remain `task_started` and `task_complete`, with `turn_started`/`turn_complete` accepted as aliases. [event policy](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/policy.rs#L133); [event enum and aliases](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/protocol/src/protocol.rs#L1583)

Legacy mode additionally saves `UserMessage`, `AgentMessage`, `AgentReasoning`, `AgentReasoningRawContent`, `EnteredReviewMode`, `ExitedReviewMode`, `PatchApplyEnd`, `ContextCompacted`, `McpToolCallEnd`, `WebSearchEnd`, and `ImageGenerationEnd`. Paginated mode represents these through completed typed items. `SubAgentActivity` is saved as a legacy event only when its kind differs from `Completed`. Legacy `ItemCompleted` survives only for `FunctionCallOutput`, `Plan`, `Extension(Sleep)`, and completed `SubAgentActivity`; paginated `ItemCompleted` survives for all `TurnItem` kinds. [completed-item policy](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/policy.rs#L242)

Every other EventMsg variant is filtered on live append, as individually listed in the matrix. This includes errors, warnings, approvals, guardian assessments, tool begin/end notifications such as `ExecCommandEnd`, hooks, streaming deltas, raw response observer events, queue changes, realtime transport notifications, and collaboration tool notifications. Their information may have a durable representation elsewhere: command completion is a typed `ItemCompleted`, raw model content is a `ResponseItem`, realtime presentation is `RealtimeItem`, and durable queue metadata has its own store. `NetworkApprovalResolved` and `PrivateSessionEvent` also carry serde skip annotations. [filtered variants](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/policy.rs#L172)

The native production path emits canonical item lifecycle notifications, then `HasLegacyEvent::as_legacy_events` converts them for compatibility consumers. Thus the same operation can emit a typed item and a legacy event while policy keeps the representation appropriate to the thread mode. `show_raw_agent_reasoning` controls generation of compatibility raw-reasoning events. The matrix includes links to these shared conversion constructors, including command, MCP, patch, review, collaboration, and reasoning conversion. [canonical-to-legacy conversion](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/protocol/src/legacy_events.rs#L70); [event fanout](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L2695)

## Tool output preprocessing before the policy

The matrix's `tool_output_preprocessing` catalog separates the original durable response envelope from the model-context copy and completed presentation item. `AnyToolResult::into_response` invokes each output converter before creating its envelope. `ContextManager::record_item_with_metadata` clones that response and applies history-budget truncation to the processed copy; the subsequent rollout batch contains the original prepared envelope. Thus context-budget reduction alone cannot be used to infer which original bytes survived in a saved response. [Output-to-envelope boundary](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/registry.rs#L307), [processed context clone](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/context_manager/history.rs#L660), [prepared envelope append](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L4153).

- **Exec and wait/poll:** unified execution holds bounded head/tail pending and transcript buffers (1 MiB each), converts retained bytes with lossy UTF-8 and omission markers, and formats the model response under requested/configured budgets with metadata space reserved. `write_stdin`/wait results can contain output chunks; terminal `CommandExecution` completion derives aggregated transcript independently. Paginated persistence then applies its 64 KiB completed-command cap. [Collection](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/unified_exec/process.rs#L46), [byte-to-text boundary](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/unified_exec/output.rs#L24), [terminal transcript](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/unified_exec/async_watcher.rs#L459), [model response budgeting](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/context.rs#L573).
- **Apply patch:** executor output becomes `ApplyPatchToolOutput`, whose response converter preserves its text. Typed `FileChange` completion copies changed paths and stdout/stderr; legacy `PatchApplyEnd` derives from that item. The central persistence policy adds no FileChange-specific output cap. [Patch response](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/context.rs#L357), [typed patch completion](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/events.rs#L600).
- **MCP:** output conversion uses a prepared tool-specific token limit or model default, normalizes unsupported original image detail, prefixes wall time, and applies serialization-allowance truncation before creating the durable response. Its typed completion independently retains invocation metadata and result/error; the paginated policy applies the separate 64 KiB result cap. [Prepared limit](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/handlers/mcp.rs#L277), [response preprocessing](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/context.rs#L229), [completed presentation](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/mcp_tool_call.rs#L1170).
- **Dynamic tools:** host content items and success map into `FunctionToolOutput`; its converter preserves content and selects text versus item-array representation. Common image/audio preparation follows. The model-context copy may be truncated while the original prepared output remains in the response record. [Dynamic response conversion](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/handlers/dynamic.rs#L143), [generic output body](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/tools/context.rs#L599).
- **Web search:** hosted search stores a raw response and derived action/query item. The standalone extension supplies a requested output budget, emits result metadata in a completed extension item and explicit legacy `WebSearchEnd`, and returns search text as a function output. Error text is explicitly bounded; the response converter preserves returned payload. [Hosted mapping](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/event_mapping.rs#L230), [standalone completion/error handling](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/ext/web-search/src/tool.rs#L199), [output converter](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/ext/web-search/src/output.rs#L40).

These paths establish concrete truncation/normalization boundaries. Their schemas can retain paths, media/file references, JSON metadata, and original text; there is no universal secret-scrubbing transformation at the writer boundary. Per-boundary unit/integration test links in the matrix describe what was checked, including exec metadata budgets/omission markers, structured MCP truncation, and image reference retention.

## Transformation and payload limits

Paginated completed command items cap `aggregated_output` at 64 KiB by middle truncation with the marker `... command output truncated for persistence ...`. Paginated completed MCP items pass results through `truncate_mcp_tool_result` with a 64 KiB budget. These transformations clone the persisted representation and preserve the original runtime event. The policy passes legacy completion payloads through unchanged. Raw ResponseItem policy performs an allowlist check; tool result content may already have been prepared or truncated upstream. The response envelope stores the originating history truncation token budget for function/custom outputs and attribution/order metadata; this budget is distinct from the completed-item byte caps. [completed payload limits](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/policy.rs#L268); [response envelope preparation](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L4033)

Retained events are explicitly bounded before persistence: oversized verified answers lose question payloads; delivered assistant messages clear text and become incomplete; selected IDs truncate to a 1,024-byte character boundary. Accepted audio records preserve IDs and are omitted when oversized by the retained-state recorder. Per-record budget is 16,384 serialized bytes; retained family snapshots cap count at eight and serialized family bytes at 65,536 by dropping oldest records and marking incompleteness. [retained budgets and bounding](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/history/src/retained_context.rs#L217); [accepted retained append](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/retained_context.rs#L158)

The central writer serializes allowed payloads. It applies no general secret/path scrub or universal binary stripping. Image preparation runs before ResponseItem persistence, with unified/detail-based budget selection, optional resize notices, the image store and ephemeral mode passed into preparation; audio preparation also runs before append. Generated-image references can remain file references or inline content, with policy tests covering both. TurnContext serialization adds compatibility sandbox fields derived from the runtime permission profile. Paths, file IDs, inline media, tool JSON, and hidden reasoning can therefore occur according to the particular payload schema and upstream preparation. Copying one JSONL file carries references whose backing media may live separately. [media preparation](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/core/src/session/mod.rs#L3915); [compatibility turn-context serialization](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/history/src/rollout_payload.rs#L86)

## Queue, bytes, barriers, and failure semantics

The recorder owns a Tokio writer task and a bounded 256-command mpsc channel. Queue saturation yields the sending future. `record_canonical_items` clones a batch and awaits enqueue; the returned success alone is queue acceptance. Commands serialize access to writer state. `AddItems` extends `pending_items` and flushes immediately once materialized; deferred AddItems remains buffered. `Persist`, `Flush`, and `Shutdown` acknowledge completed writer operations through oneshots. Successful shutdown drains then exits; failed shutdown reports its error and keeps the task alive for retry. `Discard` acknowledges and exits without draining pending items. [channel and task ownership](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L1024); [writer command loop](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L1941)

Each line is built as a complete JSON string plus newline, then passed to `write_all`, followed by `File::flush`. The record envelope has a UTC timestamp generated at write time with millisecond precision, optional ordinal, and flattened RolloutItem wire object (`type`, `payload`, plus response metadata where present). It carries no outer Event submission ID unless the payload has its own correlation field. There is no `sync_all`/`sync_data` in this JSONL write/barrier path; success establishes the implemented flush barrier rather than an explicit filesystem fsync. [JSONL envelope and writer](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L2074)

After each successful line write and flush, the ordinal advances and that item joins the prefix removed from `pending_items`. An I/O error drops the handle and retains the unwritten suffix. A barrier immediately reopens and retries once; if that fails, the caller receives the second error and future barriers can retry. Metadata clears only after its successful write. Appending opens with append semantics and repairs a non-newline-terminated tail by appending a newline. It does not remove partially written bytes. Consequently partial-write/flush errors can leave malformed fragments or cause a retried record to appear more than once; batches are not atomic and the implementation does not promise exactly-once crash recovery. Retry timestamps may differ because the envelope is regenerated. [pending-prefix and retry handling](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L1774); [append-tail repair](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/recorder.rs#L2030)

Legacy records omit ordinals. Paginated new records begin at zero or `history_base.end_ordinal_exclusive`; successful records increment with checked overflow. Reopening derives the next ordinal from the final parseable record, skipping rejected trailing lines, with history mode read from the initial metadata. It rejects a final valid paginated record without an ordinal and an incomplete inherited subagent prefix. Gaps are accepted; the next ordinal follows the last valid ordinal. Writer recovery reopens the file while retaining its existing in-memory ordinal state. [ordinal assignment and resume](https://github.com/openai/codex/blob/2bc8e7f5459b084afa482c7aac3f56fef36286b3/codex-rs/rollout/src/ordinal.rs#L17)
